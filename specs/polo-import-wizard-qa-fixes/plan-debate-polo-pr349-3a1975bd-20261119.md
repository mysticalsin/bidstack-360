1. [red-first] A stale mark cancels a later retry. Code: `cancelWasRequested` finds any row where `{ orgId, targetId: jobId, action: MIGRATION_CANCEL_REQUESTED }` (worker/queues/migration.ts), with no attempt, no time bound, and nothing deletes or consumes it. Retry reuses the same job id and only changes `meta.attemptId` (migrations.ts retry claim, `fresh.attemptId = attemptId`). Sequence: Cancel writes the mark and returns 200; the chunk dies or the stale reaper marks the job FAILED before consuming it; the user retries; the first chunk of the new attempt sees the old mark and cancels itself. Change: key the mark to the attempt, `diff: { attemptId: migrationAttemptId(job.meta) }` on write, and have `cancelWasRequested` match that attempt only. Also stamp `createdAt >= job.startedAt`. Test: write a mark under attempt A, move the job to FAILED, retry as attempt B, run a chunk, expect the rows to import and the job not CANCELLED. Mutant: drop the attempt filter and require red.

2. [red-first] Any lock holder, not only a chunk, produces a mark. Code: `catch (err) { if (!isLockTimeout(err)) throw err; outcome = 'locked'; }` then the mark insert and `return serializeJob(current)`. `isLockTimeout` also accepts any message matching `/lock timeout/i` and any `cause` with 55P03. The row can be locked by Undo, the Retry claim, the stale reaper, or a second Cancel, none of which will ever read the mark. Cancel then returns 200 with the job RUNNING and the mark sits there (feeds item 1). Change: write the mark only after confirming a live chunk, or make the mark valid only for the current attempt (item 1) and add a bounded expiry; if no chunk can consume it, return 409 with the existing status text. Narrow `isLockTimeout` to `code === '55P03'`, with the message regex only as a fallback on `PostgresError { code: "55P03"`. Tests: hold the row with a plain `SELECT ... FOR UPDATE` in another session (not a chunk) and assert Cancel does not leave a mark that a later chunk consumes; an error with message "lock timeout" but no 55P03 is rethrown.

3. [residual] The mark can land after the last check and before commit. Code: second check `if (await cancelWasRequested(tx, ...)) throw new MigrationCancelRequested()` runs before `persistChunkBookkeeping`, and the mark insert takes no lock the chunk holds, so a mark written between that check and commit is missed. If this was the last chunk, the job finishes COMPLETE and the client was told 200. Change: decision.md states the window and that the final status is the truth; `cancel` returns `cancelRequested: true` with the RUNNING job (item 4). If Tony wants it closed, the completion write must re-check the mark in the same statement (`UPDATE ... WHERE NOT EXISTS (mark)`) and still leaves a smaller race, so call it a residual either way. Test: pin the behavior, mark inserted after the second check, chunk commits, status is COMPLETE, and the response said cancel was only requested.
