# Audit Log Exports Must Be Server-Side Evidence Artifacts

## Problem

Client-side CSV exports only include the currently loaded page and cannot prove
tenant scope, export provenance, or complete filter handling. They also miss the
most important compliance invariant: the export itself must be written back to
the audit log.

## Solution

Audit exports are generated by the API as XLSX workbooks:

- Use the same tenant-scoped audit query as the read route.
- Apply export filters server-side.
- Bound rich scans with a hard maximum so diff searches cannot become unlimited
  table walks.
- Include an `Export Metadata` sheet with the export audit event id, requester,
  filters, scanned rows, exported rows, and truncation status.
- Include an `Audit Log` sheet with actor, action, target, category, risk score,
  request provenance, related CRM ids, diff summary, and full diff JSON.
- Neutralize Excel formula prefixes in every user-controlled text cell.
- Write `audit_log.export.xlsx` back to the audit log before returning the file.
- Serve with `Cache-Control: private, no-store`.
- Treat `Truncated by limit` as a compliance field, not decoration. If the
  export limit is reached inside a fetched batch, mark the export truncated even
  when there is no extra database page after that batch.

## Rule

Compliance exports are backend-owned artifacts. Do not add client-only exports
for audit, finance, security, or admin evidence unless there is also a
server-side export that is tenant-scoped, audited, bounded, and injection-safe.
Every export workbook should promote high-value forensic fields into columns so
reviewers can filter in Excel without decoding raw JSON.
