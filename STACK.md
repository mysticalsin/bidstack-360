## Conventions

- **File naming:** kebab-case for files, PascalCase for React components, camelCase for utilities.
- **Imports:** absolute via `@bidstack/<package>` workspace aliases; never `../../..`.
- **No default exports** in libraries; named exports only. Default export OK for React pages/route components.
- **Errors:** typed Result objects in libs; throw in route handlers (Fastify catches and serializes).
- **State (frontend):** Zustand for global UI state; React Query (`@tanstack/react-query`) for server state. No Redux.
- **Logging:** Pino with request-scoped child loggers. No `console.log` in shipped code.
- **CSS:** Tailwind 4 utility-first. CSS variables for theme tokens (light/dark). No styled-components.
- **Dates:** ISO 8601 strings on the wire. `date-fns` for client formatting.
- **Money:** Always store amounts in **micros** (integer × 1e6) per Twenty/Stripe convention. Format at the edge.

## Project Conduct Addenda

These rules layer on top of the universal Karpathy Four (in `CLAUDE.md` §5).
They are project-specific and override defaults where they conflict.

### Use the model only for judgment calls

When implementing systems that call an LLM, only route judgment-shaped
work to the model: classification, drafting, summarization, extraction.
Deterministic transforms, routing, retries, and parsing belong in code.
If code can answer, code answers.

### Token budgets (raised for this monorepo)

- Per-task: **15,000 tokens**
- Per-session: **100,000 tokens**

Raised from defaults (4K / 30K) because this is a >25-file monorepo.
If approaching budget, summarize and start fresh. Surface the breach.
Do not silently overrun.

### Checkpoint format

After every significant step, summarize using this exact format:

```
✅ Done:      <what's verified>
🔄 Now:       <what's running>
⏭️  Next:      <what's queued>
⚠️  Surfaced:  <conflicts, deferred work, or "none">
```

Don't continue from a state you can't describe back. If you lose track,
stop and restate.

### Read before you write

Before adding code, read exports, immediate callers, shared utilities.
"Looks orthogonal" is dangerous. If unsure why code is structured a way,
ask. (This is the Researcher role's standing instruction even when a
Builder is mid-flight.)

### Tests verify intent, not just behavior

Tests must encode WHY behavior matters, not just WHAT it does. A test
that can't fail when business logic changes is wrong. (This sharpens the
Test Verifier's acceptance-criteria mapping.)

### Surface conflicts, don't average them

If two patterns contradict, pick one (more recent / more tested),
explain why, and flag the other for cleanup. Don't blend conflicting
patterns. (Strengthens `CLAUDE.md` §10 conflict-resolution priority.)

### Confirm before destructive operations

Force-push, `rm -rf` on anything not in `/tmp`, dropping tables,
deleting branches, rewriting history, truncating data, and any
operation that loses work require explicit confirmation. No exceptions
for "I'm sure." (Reinforces `CLAUDE.md` §6 Don't-Do.)

## Design system

Per `~/.claude/rules/design-standards.md` (still active globally) and
the Apple HIG referenced in the handoff:

- Apple HIG component principles
- 8px spatial grid; 9-step type scale
- **Dark mode is mandatory, not optional**
- Every interactive component ships **all states**: default / hover / focus (2px ring, 3:1 contrast) / active / loading / error / empty / disabled / success
- WCAG 2.2 AA: 4.5:1 normal text, 3:1 large text, 44×44px touch targets, full keyboard nav, `prefers-reduced-motion` respected
- Performance: LCP < 2.5s · INP < 200ms · CLS < 0.1
- Images: WebP/AVIF, lazy loading, responsive `srcset`
