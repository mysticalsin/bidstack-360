# Security policy

We take the security of BidStack 360° seriously. This document tells you what is in scope, how to report a vulnerability, what to expect from us, and the legal protections that apply when you act in good faith.

## Reporting a vulnerability

Email **security@mantu.com** with a clear description of the issue.

Please include:

1. A summary of the issue (one or two sentences).
2. Affected component(s) — e.g. `apps/api`, `apps/web`, `apps/mcp-server`, `apps/worker`, the public REST API surface, a third-party integration, a Helm chart, or a CI workflow.
3. Reproduction steps — request shape, payload, observed response, expected response.
4. Impact — what an attacker could do with this issue (data exposure, mutation, lateral movement, denial of service, etc.).
5. Any proof-of-concept that helps us reproduce the issue. We prefer minimal PoCs over exploit code; the goal is to fix it, not to weaponise it.
6. Your name or handle for credit, if you would like to be acknowledged.

If your report is sensitive enough that email-in-transit is itself a concern, request our PGP key in the first message and we will reply with it before you send details. We will not ask for credentials or personal data from you.

We acknowledge every report within **2 business days**. If you have not heard from us within that window, please retry or open a private GitHub Security Advisory on the repository.

## What is in scope

- The main BidStack 360° API (`apps/api`)
- The web client (`apps/web`)
- The worker (`apps/worker`) and the MCP server (`apps/mcp-server`)
- The shared packages under `packages/` that are imported by any of the above
- The public production deployment (URL provided on first contact)
- CI workflows under `.github/workflows/` that build or deploy the above
- Build-time supply-chain attacks against this repository

## What is out of scope

The following are explicitly **out of scope** for the bug bounty / acknowledgement program, but we still want to hear about them — just label them clearly so we triage them appropriately:

- Issues in third-party dependencies that are already published CVEs and where we are within the standard patch SLA (track `pnpm audit` output for the current state)
- Vulnerabilities only exploitable with a privileged role acting outside their authorisation (i.e. an admin doing admin things — that is not a vulnerability, that is a personnel matter)
- Social engineering of Mantu employees or contractors
- Denial of service via volumetric attack (we trust our CDN / cloud provider for this layer)
- Vulnerabilities requiring physical access to a user's device or browser
- Self-XSS (you XSS yourself in your own session)
- Missing security headers that have no demonstrable impact on this specific application (e.g. missing `X-Permitted-Cross-Domain-Policies` on an endpoint that never returns Flash content)
- Software version disclosure without a corresponding exploitable vulnerability
- Issues in the dev-only stub auth path (active only when `CLERK_SECRET_KEY` is unset and `NODE_ENV !== 'production'`)
- Findings against staging or developer environments that are not reachable from production traffic paths
- Reports generated by automated scanners with no manual validation

## What we will do

When you report a valid issue, we will:

1. **Acknowledge** receipt within 2 business days.
2. **Triage** and assign a severity (Critical / High / Medium / Low / Informational) within 5 business days.
3. **Communicate** a remediation plan — what we will change, and on what timeline. For Critical issues, this is days; for High, weeks; for Medium / Low, within the next release cycle.
4. **Fix** the issue and verify the fix. We may ask you to re-test the fix.
5. **Disclose** publicly once the fix is deployed and we have given existing customers reasonable time to update. Our default disclosure SLA is **90 days from the date you reported the issue**, extendable by mutual agreement if the fix needs more time.
6. **Credit** you in the disclosure if you wish to be named.

## What we ask of you

In return, when you act in good faith:

- Give us reasonable time to fix the issue before any public disclosure (default: 90 days from your report, but we will negotiate genuine extensions if the fix is complex).
- Do not access, modify, exfiltrate, or destroy any data that does not belong to you. If you can demonstrate the impact with a synthetic / your own test account, please do.
- Do not run sustained automated scans against our production environment.
- Do not perform any test that degrades service for other users (volumetric DoS, lockout-account brute force, etc.).
- Do not use the vulnerability to pivot deeper than necessary to demonstrate the issue.

## Safe harbour

We will not pursue civil action, file a criminal complaint, or alert law enforcement for security research that:

1. Acts in good faith.
2. Avoids data destruction, service disruption, and access to data that does not belong to you.
3. Reports the issue to us privately at security@mantu.com before any public disclosure.
4. Stays within the scope defined above.
5. Gives us a reasonable opportunity (the 90-day SLA above, or as we mutually agree) to fix the issue before disclosing.

This safe harbour applies to your research activity, not to any unrelated misuse of the platform. Vulnerabilities found incidentally during normal use of the product are also covered — you do not need to declare yourself a security researcher up front.

If a third party (a customer, partner, or law-enforcement agency) initiates legal action against you for research conducted in compliance with this policy, we will publicly state that your activity was authorised.

## Coordinated disclosure timeline

The default timeline from your first report to public disclosure:

| Day                  | Event                                                       |
| -------------------- | ----------------------------------------------------------- |
| 0                    | You report the issue                                        |
| ≤ 2 business days    | We acknowledge receipt                                      |
| ≤ 5 business days    | We confirm severity and remediation plan                    |
| Per severity         | We fix (Critical: days; High: weeks; Med/Low: next release) |
| Fix + soak           | We verify in production                                     |
| ≤ 90 days from day 0 | Public disclosure (or earlier if you and we agree)          |

If the issue is being actively exploited, we will accelerate this aggressively. If the fix is genuinely impossible within 90 days (e.g. it requires coordination with multiple upstream maintainers), we will agree on an extension with you in writing.

## Acknowledged researchers

We maintain a public hall of fame in the project documentation. If you would prefer not to be named, we respect that — just tell us in your report.
