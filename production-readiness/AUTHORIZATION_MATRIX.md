## 1. How auth/authz works here (critical context)

- **Global authentication:** `auth.ts` `onRequest` hook authenticates EVERY request (Clerk JWT / API key / dev stub) unless the route sets `config:{ public:true }`. A mutation with no `preHandler` is therefore still **authenticated** â the risk is **broken authorization** (a read-only-role user, or a read-scoped API key, can mutate), not unauthenticated IDOR.
- **`requirePermission(key)`** (`rbac.ts`): for human users, checks a `UserRole â RolePermission` grant for the exact permission key â **no admin-claim fallback; the DB authorizes**. For REST API keys (`role === 'api'`), production checks the exact permission scope (for example `integrations:write`). Legacy broad `read`/`write` fallback is enabled only outside production by default, or by explicit `BIDSTACK_ALLOW_LEGACY_API_KEY_SCOPES=true` during migration.
- **`requireRole(...names)`** (`rbac.ts`): always 403s API keys; otherwise checks the named role via `UserRole`. (Hardened this session line of work â see [SECURITY_REVIEW](./SECURITY_REVIEW.md): API-role principals are now explicitly rejected and role lookup is DB-authoritative + case-insensitive.)
- **Consequence:** a route with NO permission/role gate (per-route or file hook) has ZERO permission check, so any authenticated principal, including an API key that passes global auth, can invoke it.

## 5. Design risks & follow-ups

- **Access policy enforcement scope.** With `ACCESS_POLICIES_ENFORCE=true`, the published policy narrows `requirePermission` checks for human sessions only. API-key requests and field-level `hasPermission` checks still follow the RBAC matrix alone. Record conditions (country) are not enforced at route level because the record is not loaded there; the simulation reports those changes as `recordOnly`. Each API instance caches the published policy and subjects for 15 seconds, so a publish reaches other instances within that window. If stored rules fail validation, every policy-governed request is denied until a valid version is published.

- **Closed this pass:** REST API keys are no longer resource-agnostic in production. `requirePermission` now accepts exact `PermissionKey` scopes and rejects broad `read`/`write` unless the legacy migration flag is explicitly enabled. MCP transport keeps its separate `mcp` + `read`/`write` tool-class scopes.
- **Closed this pass:** AI compute routes now have behavioral 403 regression tests for API keys with exact REST scopes. The remaining harness follow-up is broader non-admin human simulation, not the API-key path.
- **Confirm:** every public webhook/OAuth endpoint verifies its signature/token/state (spot-checked: Twilio `X-Twilio-Signature`, Dust signature, OAuth `state` â all present).
